> **30초 요약** — HashMap + **모든 엔트리를 잇는 이중 연결 리스트**.
> 조회는 여전히 O(1)인데, **넣은 순서(또는 최근 접근 순서)대로 순회**된다.

## 어떻게 생겼나

- 엔트리마다 `before`, `after` 포인터가 하나씩 더 붙는다.
- 생성자 세 번째 인자 `accessOrder`
  - `false`(기본) → **삽입 순서**
  - `true` → **접근 순서** (`get`하면 맨 뒤로 이동)
- `removeEldestEntry()`를 오버라이드하면 put 직후 **가장 오래된 엔트리를 자동 제거**할 수 있다.

## 강점

- HashMap과 같은 **O(1)** 연산
- **예측 가능한 순회 순서** — 테스트 결과, JSON 직렬화 순서가 매번 같다
- LRU 캐시를 사실상 공짜로 얻는다
- Java 21부터 `SequencedMap` — `firstEntry()`, `lastEntry()`, `pollFirstEntry()` 지원

## 약점

- 엔트리마다 포인터 2개 → HashMap보다 **메모리를 조금 더** 쓴다
- 스레드 안전하지 않다 (LRU를 여러 스레드에서 쓰려면 동기화 필요, 혹은 Caffeine 같은 라이브러리)

## 이럴 때 쓴다

- 입력 순서를 유지해야 하는 설정값, 헤더, 폼 필드
- "중복 제거하되 처음 나온 순서 유지"
- 간단한 **LRU 캐시**

```java
// 10줄 LRU 캐시
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(16, 0.75f, true);   // accessOrder = true
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity; // 넘치면 가장 오래 안 쓴 것 제거
    }
}
```

## 기억할 것

- **순서 + O(1)** 이 동시에 필요하면 LinkedHashMap
- "순서"가 *삽입 순서*가 아니라 *키의 크기 순서*라면 → `TreeMap` (5편)
- 운영 캐시는 만료·통계·동시성까지 필요하니 Caffeine을 고려
