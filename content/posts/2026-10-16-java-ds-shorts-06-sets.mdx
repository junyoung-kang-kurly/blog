> **30초 요약** — `HashSet`은 사실 **값을 버린 HashMap**이다. TreeSet은 TreeMap, LinkedHashSet은 LinkedHashMap.
> 그래서 Map을 고르는 기준이 그대로 Set에 적용된다. enum이면 무조건 **EnumSet**.

## 한눈에 비교

| | 내부 구현 | 순서 | 주요 연산 | null |
|---|---|---|---|---|
| `HashSet` | HashMap | 없음 | O(1) | 1개 허용 |
| `LinkedHashSet` | LinkedHashMap | 삽입 순 | O(1) | 1개 허용 |
| `TreeSet` | TreeMap | 정렬 순 | O(log n) | 불가(기본 정렬) |
| `EnumSet` | **비트 벡터** | enum 선언 순 | O(1), 초고속 | 불가 |

## 각자의 강점

- **HashSet** — 중복 제거, 멤버십 체크(`contains`)의 기본값
- **LinkedHashSet** — 중복 제거하면서 **처음 등장한 순서 유지**
- **TreeSet** — 정렬된 집합 + `floor`, `ceiling`, `headSet`, `subSet` 범위 질의
- **EnumSet** — enum 상수를 `long` 비트로 표현. `contains`가 비트 연산 한 번. 메모리도 거의 0.

## 약점·주의

- Set에 넣은 객체를 **바꾸면** 찾지 못한다 (HashMap 키와 같은 문제)
- `HashSet`의 순회 순서에 의존하는 코드는 언젠가 깨진다
- `TreeSet`에서 `compareTo`가 0이면 **같은 원소**로 보고 버린다 — 정렬 기준이 동점인 객체가 사라지는 버그의 단골 원인

## 이럴 때 쓴다

```java
// 중복 제거 + 순서 유지
Set<String> uniqueTags = new LinkedHashSet<>(rawTags);

// 방문 체크
Set<Long> visited = new HashSet<>();
if (!visited.add(nodeId)) return; // add가 false면 이미 있음

// 정렬 + 가장 가까운 값
TreeSet<Integer> slots = new TreeSet<>(List.of(9, 12, 15, 18));
Integer next = slots.ceiling(13); // 15

// 권한·상태 플래그는 EnumSet
EnumSet<Permission> perms = EnumSet.of(Permission.READ, Permission.WRITE);
boolean canWrite = perms.contains(Permission.WRITE);
```

## 기억할 것

- Set 고르기 = Map 고르기: **기본 HashSet / 순서 LinkedHashSet / 정렬 TreeSet**
- 키가 enum이면 Set은 `EnumSet`, Map은 `EnumMap` — 성능과 가독성 모두 이득
- `add()`의 반환값(boolean)을 활용하면 `contains` + `add` 두 번 호출을 줄인다
